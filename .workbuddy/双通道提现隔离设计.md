# 双通道提现隔离设计（来电有喜）

> 版本：v1.0 · 2026-07-30
> 关联任务：#44 / #45 / #46 / #48（双通道隔离实现）、#49 / #50（CI 落地，本设计被 `code-review-standards.md §4.5` 引用）
> 适用范围：用户侧「推广佣金→健康豆」通道 与 门店侧「货款结算」通道 的彻底隔离

---

## 1. 背景与硬约束

历史实现中，门店货款提现与用户佣金提现**共用同一张 `withdrawals` 表**，且门店侧创建提现时**漏写 `kind` 字段**，被 `withdrawals.kind` 的默认值 `'commission'` 污染，导致：

- 门店货款提现被混入「用户佣金」通道，后台按 `kind` 审核 / 计税 / 对账时出现**错账**；
- 门店页曾错用 `getCommissionBalance`（旧佣金表余额）并标注「佣金提现」，语义与数据均错。

**硬约束（来自历史裁定与合规标准）：**

| 约束项 | 内容 |
| --- | --- |
| 佣金去向 | 推广佣金按 **50% 可提现佣金(`commission_balance`) + 50% 健康豆(`tb_balance`)** 发放（自 2026-07-29 起，见 `distribute-commission`）；可提现一半走提现通道，健康豆一半仅平台内消费 |
| 健康豆属性 | 健康豆(`tb_balance`)那一半**不可提现 / 不可兑现金**，仅限平台内消费；可提现佣金(`commission_balance`)一半可提现 |
| 货款提现 | 走**微信服务商分账**直达门店子商户号，属合法可提现资金 |
| 术语红线 | 禁「情绪豆 / 通宝 / 分销佣金 / 团队业绩 / 飞轮」；「微信服务商分账」为微信支付官方产品名，**合法**，不在禁用范围 |

## 2. 双通道模型总览

```
┌─────────────────────────────────────────────────────────────────────┐
│  通道 A（用户侧 · 推广佣金）           通道 B（门店侧 · 货款结算）      │
├─────────────────────────────────────────────────────────────────────┤
│  kind        = 'commission'          kind        = 'settlement'      │
│  owner_type  = 'user'                owner_type  = 'store'           │
│  资金来源    推广佣金 → 50% commission_balance + 50% 健康豆  │  资金来源    merchant_settlement  │
│  可提现？    ✅ 50% 可提现（commission_balance）  ✅ 微信服务商分账可提现          │
│  入口        佣金明细页 → 提现页(trade/withdraw)  门店中心「货款提现」页            │
│  余额查询    getMyBalance().commission_balance   fn_get_store_settlement         │
│  提现动作    applyWithdraw()（用户提交，人工打款）  fn_merchant_withdraw（原子 RPC）│
└─────────────────────────────────────────────────────────────────────┘
```

两通道在**同一张 `withdrawals` 表**共存，靠 `kind` + `owner_type` + `store_id` 三列组合区分，绝不交叉。

---

## 3. 数据模型

### 3.1 `withdrawals`（迁移 00120）

```sql
kind text NOT NULL DEFAULT 'commission'
  CHECK (kind IN ('commission','settlement'))
```

- 默认值 `'commission'` 是**用户通道的安全兜底**：任何省略 `kind` 的写入都会落入用户通道，不会污染门店结算。
- 门店通道**必须显式写 `kind='settlement'`**（见 §5 修复点 1），不能依赖默认。

### 3.2 `merchant_settlement`（门店货款结算余额）

- 门店可结算货款、冻结金额、累计已结算、结算单计数等字段。
- 通过 RPC `fn_get_store_settlement(p_store_id)` 读取，避免前端直查表导致的权限/口径问题。

### 3.3 收款账户隔离

- 已保存收款账户按 `owner_type` 区分：`user`（用户佣金/健康豆相关） vs `store`（门店货款）。
- 门店「货款提现」页**只查询/写入 `owner_type='store'`** 的账户，杜绝账户串用。

## 5. 隔离保证（防错账机制）

1. **显式 kind（最关键）**：`createWithdrawal` 在 `withdrawals.insert` 时**强制写 `kind:'settlement'`**，并加注释说明硬约束，杜绝默认 `'commission'` 污染。
2. **原子 RPC**：门店提现走 `fn_merchant_withdraw(p_store_id, p_user_id, p_amount, p_method, p_account)`，服务端预扣 `merchant_settlement` + 写提现单 + 关联结算单，单事务保证「余额不足不写单」「写单必扣减」。
3. **余额口径隔离**：门店页**不再**调用 `getCommissionBalance`（旧佣金表），统一改用 `fn_get_store_settlement` 结算余额。
4. **账户隔离**：收款账户按 `owner_type` 物理隔离，门店页只操作 `store` 账户。
5. **记录过滤**：门店提现记录列表按 `kind='settlement'` 过滤，后台审核/对账只看到本通道单据。

## 7. 合规术语口径（被 CI 引用）

- **禁旧词（硬门禁，源码已零命中）**：情绪豆、通宝、分销佣金、团队业绩、飞轮。
- **合法功能名（不在任何扫描层）**：微信服务商分账（微信支付官方产品，门店货款结算正是用它）。
- **去 AI 化（硬门禁）**：源码不得出现「人工智能 / 大模型」表述。
- **提示性（仅警告，不阻断）**：`AI` 字面（如 `decided_by==='ai'` 徽章）、医疗宣称词（治疗/治愈/抗炎/降血压/根治/补肾，需排除词库定义文件与「治愈系」情绪标签）。
